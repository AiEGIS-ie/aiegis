## Purpose

Specify exactly HOW an AiEGIS agent's identity binds to silicon at OS-boot, satisfying Trav's 4 invariants:
1. **Permanent** — survives process restart, container re-deploy, OS reboot
2. **Cannot-be-touched** — private key never leaves hardware, not exportable
3. **Non-volitional** — agent doesn't choose when/whether to attest; substrate signs
4. **Single attachment point** — one logical agent identity, multiple hardware-bound physical instantiations possible (different substrates per device)

## Three substrate lanes

Every AiEGIS agent gets ONE host-substrate binding per device. The substrate is chosen at install-time based on detected hardware. The agent has no choice; install-time policy picks.

### Lane A: TPM 2.0 (Linux/Windows servers + workstations)

**Hardware floor:** TPM 2.0 chip (discrete or fTPM). Available on:
- Windows 11 (Microsoft mandates TPM 2.0)
- Windows Server 2022+
- Linux servers with TPM 2.0 chip (most enterprise hardware ≥ 2018)
- Cloud VMs with vTPM (Azure Confidential VM, AWS Nitro vTPM, GCP Shielded VM)

**Identity binding chain:**
1. **Endorsement Key (EK):** burned into TPM at manufacture by Infineon/STMicro/Intel. Non-extractable. Identifies the physical TPM chip uniquely.
2. **Attestation Identity Key (AIK):** derived from EK at AiEGIS install-time. Used for signing. Privacy-preserving (multiple AIKs from one EK).
3. **Platform Configuration Registers (PCRs):** bank of 24 measurement slots. PCR-0..15 store boot-chain hashes. AiEGIS uses PCR-10 (or vendor-allocated) to measure aiegis-agent binary at process-startup.
4. **TPM Quote:** TPM signs (with AIK) a struct containing { PCR-values, nonce-from-verifier, timestamp }. Verifier checks: AIK certificate chain (back to TPM vendor root) + PCR values match expected aiegis-agent binary hash + nonce freshness.

**Identity primitive:** `did:aiegis:tpm:<ek-pub-multibase>:<aik-pub-multibase>` where both pubkeys are extractable but private parts are NOT.

**Unbind test:** ❌ Agent cannot extract EK or AIK private. ✅ PASSES non-volitional.

### Lane B: Apple Secure Enclave + App Attest (macOS, iOS, iPadOS, watchOS)

**Hardware floor:** Apple Silicon (M1+, A11+) or T2 (Intel Macs 2017-2020). All Apple Silicon Macs + iPhone 8+ + most iPads.

**Identity binding chain:**
1. **Secure Enclave (SE):** dedicated security coprocessor on every Apple Silicon chip. Generates and stores keys. Never exposes private key material to AP (Application Processor).
2. **App Attest API** (`DCAppAttestService`): Apple-provided framework. App requests key generation; SE generates ES256 keypair with hardware-backed attestation certificate chain back to Apple's root CA.
3. **Assertion generation:** AiEGIS agent on Mac/iPhone uses `generateAssertion(challenge)` — SE signs a server-provided nonce with the attested key. Server verifies the signature + the original attestation chain.

**Identity primitive:** `did:aiegis:apple-se:<attested-pubkey-multibase>` where the chain proves "this pubkey was generated by Secure Enclave on Apple device with team-id X".

**Unbind test:** ❌ Agent cannot extract SE-held key. ✅ PASSES non-volitional. ⚠ Apple can revoke app attestation chain — single-vendor dependency.

### Lane C: Intel TDX / AMD SEV-SNP / ARM CCA (cloud confidential compute)

**Hardware floor:**
- Intel TDX (Trust Domain Extensions): Sapphire Rapids+, Emerald Rapids+ Xeon CPUs (2023+)
- AMD SEV-SNP (Secure Encrypted Virtualization - Secure Nested Paging): EPYC 7003+ Milan, EPYC 9004+ Genoa (2021+)
- ARM CCA (Confidential Compute Architecture): ARM v9+ specifications (rolling out 2024-2025)

**Identity binding chain:**
1. **Trust Domain / Confidential VM:** AiEGIS agent runs inside an encrypted VM. Memory + CPU state encrypted; hypervisor cannot read.
2. **TD-Report (Intel) / SEV-SNP Attestation Report:** generated by hardware on demand. Contains: { measurement of VM image, current TD state, REPORTDATA field where AiEGIS embeds nonce+agent-pubkey }. Signed by CPU hardware root key (Intel/AMD provisioning).
3. **DCAP-style verifier:** Intel TDX uses DCAP (Data Center Attestation Primitives) for chain validation. AMD has KDS (Key Distribution Service). AiEGIS operator-side verifier consumes the attestation report + validates chain.

**Identity primitive:** `did:aiegis:tee:<cpu-vendor>:<vm-measurement-hash>:<agent-pubkey-multibase>`. Composed identifier captures vendor + measured-VM-image + agent-claimed-key.

**Unbind test:** ❌ Agent cannot exfiltrate from TEE (hardware-encrypted memory). ✅ PASSES non-volitional. ⚠ Single-vendor dependency per deployment (Intel OR AMD OR ARM, not portable mid-flight).

## Multi-substrate logical agent (single attachment point invariant)

A single logical agent can have multiple physical bindings across substrates. Example: a customer's AiEGIS agent runs on (a) their Mac (Apple SE), (b) their Linux server (TPM 2.0), (c) their AWS Nitro Enclave (Intel TDX). All three present DIFFERENT host-substrate DIDs but resolve to the SAME logical `did:aiegis:agent:<logical-pubkey>` via:

1. Logical agent gets one `did:aiegis:agent:<logical-pubkey>` at operator-side issuance.
2. Per-device, agent acquires a host-substrate binding (Lane A/B/C as appropriate).
3. **Binding ceremony:** logical agent signs a `BindingProof` linking its logical pubkey to the host-substrate pubkey. BindingProof includes: { logical_pubkey, host_substrate_did, host_attestation_blob, timestamp }, signed by operator (not by agent — non-volitional).
4. Verifier sees both DIDs + the operator-signed BindingProof = trust chain.

This satisfies Trav's invariant 4 (single attachment) WHILE supporting cross-device agents (Microsoft Entra/Google/AWS can't do this).

## Boot-time identity acquisition

**Lane A (TPM):**
- aiegis-agent reads `/dev/tpm0` (Linux) or `tpm.h` API (Windows)
- Generates AIK at install-time via `tpm2_createak` (or equivalent), persists EK+AIK pubkeys
- Per-request: `tpm2_quote` with nonce → 240-byte signed quote → wire to verifier

**Lane B (Apple SE):**
- App calls `DCAppAttestService.generateKey()` at first-install
- Persists keyID; per-request: `attestKey()` then `generateAssertion(nonce)` → wire to verifier

**Lane C (TEE):**
- aiegis-agent runs inside TD/SEV-VM (deployment-time orchestration)
- At start: requests TD-Report via `tdcall` (or SEV equivalent)
- Embeds nonce + agent-pubkey in REPORTDATA field
- DCAP/KDS chain validates report signature → wire to verifier

## Rate-limit + auth integration (per Nel 19:26 audit-finding)

For v0.6's rate-limiter to compose with host-substrate binding:
- Rate-limit key MUST consume the host-attested pubkey (Lane A AIK / Lane B SE-attested key / Lane C VM-measurement+agent-pubkey), NOT the bearer header alone.
- v0.6 today: `_rl_key()` reads `X-AiEGIS-Key` or `X-Agent-Id` — spoofable. **v0.7 MUST replace with attested-pubkey-fingerprint.**
- Implementation: add header `X-Aiegis-Host-Attestation` carrying the attestation blob; rate-limiter validates blob signature + extracts attested pubkey as key.

**End-to-end composition flow** (each step empirically verified tonight):

1. Agent host runs `acquire_substrate_attestation(nonce, pubkey)` → returns substrate dict (Lane A/B/C shape).
2. Two entry points produce a W3C VC bundle with substrate field + operator-signed eddsa-rdfc-2022 proof:
   - **Standalone**: `aiegis-compliance-bundle/generator.py::build_bundle(events, operator_priv, operator_did, customer_did, valid_from, valid_until, classifier_version, policy_bundle, substrate_attestation=<dict>)` — 9 args, operator-key passed explicitly.
   - **SDK customer surface**: `aiegis_agent.compliance.build_compliance_bundle(agent, events, customer_did, valid_from, valid_until, policy_bundle, substrate_attestation=<dict>)` — 7 args. The `agent` object encapsulates `operator_priv` + `operator_did` + `classifier_version`. Customers use this; the SDK wraps the operator-key custody.
3. Bundle's `@context` array dereferences to live `https://aiegis.ie/ns/compliance/v1` + `https://aiegis.ie/ns/substrate/v1` (HTTP 200, application/ld+json).
4. Regulator/auditor consumes bundle: calls `verify_bundle(bundle, operator_pub)` → checks operator signature. Then extracts substrate field + dispatches to `verify_tpm_quote` / `verify_apple_se_assertion` / `verify_tee_attestation` per Lane. Each returns field-level result struct with discrete failure reasons (auditable trail).
